- there are multiple counters or multiple locks involved by mistake

Only if correctly synchronized code still fails would you start suspecting a broken lock implementation, which is much less common.

2. If I wrap every read and write to shared variables in a lock, does that mean my program cannot have any race conditions?
A)
Not necessarily.

If every access to shared mutable state is protected by the correct lock, then you avoid the usual **data races** on that state. But your program can still have other kinds of race conditions.

### Important distinction
- **Data race**: two threads access the same memory concurrently, at least one is a write, and there is no proper synchronization.
- **Race condition**: broader; correctness depends on timing/interleaving of threads.

### Example
Even with locks around individual reads/writes, you can still get a race if a larger operation is not atomic.

```python
# Thread-safe read/write individually, but not the whole check-then-act sequence
with lock:
    if balance >= 100:
        pass

with lock:
    balance -= 100
```

Another thread could change `balance` between those two locked sections.

To make it correct, the whole operation must be under the same lock:

```python
with lock:
    if balance >= 100:
        balance -= 100
```

### So the answer is
- **No**, locking every read/write does **not automatically** eliminate all race conditions.
- It helps prevent **unsynchronized memory access**.
- But you also need to ensure that **whole invariants and multi-step operations** are synchronized correctly.

3. I’ve read that programs use virtual addresses and that these get translated to physical addresses. But if every memory access has to go through a translation step, isn’t that really slow? Why would any system accept that overhead?
A)
Yes — if every access required a full lookup in memory tables, it would be far too slow.

That’s exactly why modern systems don’t do the expensive translation from scratch every time.

### Why systems still use virtual addresses
Virtual addressing gives the OS major benefits:

- **Protection**: one process can’t freely access another’s memory
- **Isolation**: each process gets its own address space
- **Flexibility**: memory can be placed anywhere in physical RAM
- **Sparse address spaces**: heap, stacks, mapped files can grow independently
- **Useful features**: paging, copy-on-write, memory-mapped files, etc.

So the overhead is accepted only because the system gets a lot in return.

### How the overhead is made small
Processors use a **TLB** (Translation Lookaside Buffer), which is a **cache of recent virtual→physical translations**.

Since programs often access the same pages repeatedly or nearby addresses:

- if the translation is in the **TLB** (**TLB hit**), translation is very fast
- only on a **TLB miss** does hardware need to walk the page tables, which is slower

This works well because memory accesses usually have **locality**:
- nearby instructions are often on the same page
- nearby data is often reused soon

So many accesses reuse the same cached translation.

### Intuition
Without a TLB:
- one load/store might require several extra memory accesses just to find the physical address

With a TLB:
- most accesses pay only a very small extra cost

### Bottom line
Virtual memory would be too slow **without caching**.  
It is practical because hardware uses **fast translation caches (TLBs)** and related cache design tricks so that the expensive translation happens only occasionally.

B)
It would be too slow if the CPU had to do a full translation from scratch on every memory access.

The reason it’s acceptable is: **modern CPUs cache address translations**, mainly in a structure called the **TLB** (**Translation Lookaside Buffer**).

### What happens in practice
- A program uses a **virtual address**.
- The CPU first checks the **TLB** to see whether it already knows the corresponding physical address.
- If it’s a **TLB hit**, translation is very fast.
- Only on a **TLB miss** does the CPU need to do more work, like consulting the page table in memory.

So most accesses do **not** pay the full translation cost.

### Why systems still want virtual memory
Because the benefits are huge:
- **Process isolation / protection**: one program can’t easily read or overwrite another’s memory.
- **Simpler programming model**: each process gets its own virtual address space.
- **Efficient memory management**: pages can be moved, shared, or swapped without programs noticing.
- **Features like shared libraries, memory-mapped files, copy-on-write**, etc.

### So the tradeoff is
- **Cost**: some translation hardware and occasional misses
- **Benefit**: safety, flexibility, and much easier OS memory management

In short: **yes, translation adds overhead, but hardware caching makes the common case fast, and the OS-level benefits are worth it**.

4. What problem does paging solve relative to giving each process a contiguous region of physical memory?
A)
Paging solves the **external fragmentation and relocation problem**.

If each process must occupy one **contiguous** chunk of physical memory, then over time memory gets broken into scattered free holes. You might have enough total free memory for a process, but **not one large enough contiguous block** to hold it.

Paging avoids this by:
- splitting physical memory into fixed-size **frames**
- splitting a process’s virtual memory into same-size **pages**
- allowing pages to be placed in **any free frames**, not all together

So the main benefit is:
- **no need for contiguous physical allocation**
- much less **external fragmentation**
- easier memory allocation and process growth/swapping

There can still be a little **internal fragmentation** in the last page, but paging mainly fixes the problems caused by requiring contiguous physical memory.
B)
Paging solves the **placement and allocation problem** of contiguous physical memory.

If each process needed **one contiguous block** of physical memory, the OS would have trouble when free memory is split into many small holes. Even if the **total** free memory is enough, there may be no **single large contiguous region** big enough for the process. This is the classic **external fragmentation** problem.

With paging:

- physical memory is split into **fixed-size page frames**
- a process’s memory can be placed in **many separate frames**
- the page table makes those scattered frames look like one **linear virtual address space**

So paging lets the OS:

- allocate memory much more easily using free frames
- place parts of a process **anywhere** in physical memory
- pack memory more efficiently
- avoid the need to find large contiguous regions

In short: **paging removes the requirement that a process occupy one contiguous physical block, which avoids external fragmentation and makes memory allocation much simpler.**

5. I read that FAT file systems follow a chain of entries to find all the parts of a file. Why would anyone design a file system that way instead of just storing the full list of block locations in one place?
A)
Because it makes the on-disk metadata **very simple and flexible**, especially for early systems.

### Why use a chain?
In FAT, each cluster points to the **next cluster** of the file. That means:

- **Files can grow easily**  
  If a file gets bigger, you just add another free cluster and update one FAT entry.  
  You don’t need to move or rewrite a big “list of all blocks.”

- **Directory entries stay small**  
  The directory only needs to store the **first cluster**.  
  The rest is found by following the chain.

- **Works even when storage is fragmented**  
  The file’s clusters can be anywhere on disk. The chain links them together.

- **Implementation is simple**  
  This was attractive for early computers with limited memory and simple operating systems.

### Why not store the whole list in one place?
That approach also exists in other file systems, but it has tradeoffs:

- If the list is stored in one fixed-size place, it may **run out of room** for large files.
- If the file grows, the metadata list may need to **grow too**, which can require moving or reorganizing metadata.
- You need a more complex structure to handle very large files efficiently.

### Main downside of FAT’s chain design
The big cost is **access speed**:

- To reach the 100th cluster, you often have to follow the first 99 links.
- If the file is fragmented, reading can be slower.
- If part of the chain is corrupted, the rest of the file may become hard to find.

### In short
FAT uses chaining because it is a **simple, compact, and easy-to-grow design**, even though it is less efficient than more advanced file systems for large or heavily fragmented files.

B)
Because FAT is optimizing for **simplicity**, not for the best random-access performance.

In FAT, each block has one entry in the File Allocation Table, and that entry points to the **next block** of the file (or EOF). So a file is stored like a linked list across the disk.

Why design it this way?

- **Easy to grow files**: if a file gets bigger, the system can just allocate one more free block and link it to the end. No need to move or resize a central “list of block numbers.”
- **Simple metadata structure**: FAT uses one uniform table for both:
  - tracking a file’s block chain
  - tracking free space (`FAT[i] = 0` means block `i` is free)
- **Low design complexity**: early systems valued being easy to implement and widely compatible.

Why not store the whole block list in one place?

- Then that list must itself have space somewhere.
- If the file grows beyond the space reserved for that list, you need extra mechanisms:
  - move the list,
  - extend it,
  - or add indirect structures.
- That makes the file system more complex.

Main downside of FAT’s chain design:

- **Poor random access**: to find block 1000 of a file, you may need to follow the chain through the earlier entries.
- It can also lead to **fragmentation** if blocks are allocated one by one.

So the short answer is:

> FAT uses chains because it makes allocation and growth very simple, even though it sacrifices access efficiency compared to storing a full block index in a more structured way.

- **FAT** uses a table linking blocks together.
- **NTFS** uses a master file table.
- **Unix-like systems** often use **inodes**.

7. If threads in the same process share the same address space, why don’t they also each need their own completely separate copy of the program’s code and global variables?
A)
Because **sharing** is the point of threads.

- A **process** is the unit that owns resources like:
  - the **address space**
  - the program’s **code**
  - **global/static variables**
  - open files, etc.

- A **thread** is just an execution path *inside* that process.

So threads **do not need separate copies** of code and globals because they are all running in the **same process memory**.

What each thread **does need its own copy of** is the stuff that depends on its individual execution state:
- **program counter / instruction pointer** — where this thread is currently executing
- **registers**
- **stack** — for function calls, local variables, return addresses

### Why code can be shared
The program code is usually **read-only**, so many threads can execute the same instructions safely at the same time.

### Why globals are shared
Global variables are part of the process’s memory. Since all threads share that memory, they all see the same globals.

That is also why threads can communicate easily — but it’s also why **race conditions** can happen if multiple threads modify the same global data without synchronization.

### Simple analogy
Think of a process as a **house**:
- the **code and globals** are the shared rooms and furniture
- each **thread** is a person in the house
- each person has their own **call stack and current activity**, but they use the same house

So: **separate threads need separate execution state, not separate copies of the whole program memory.**
B)
Because **sharing the address space** means the threads can all **see the same memory**, and that is exactly what we want for **code** and most **global data**.

### What each thread needs its own copy of
A thread needs its own **execution state**, such as:
- **program counter**
- **registers**
- **stack**

These are different because each thread may be:
- executing a different function call,
- at a different instruction,
- with different local variables.

### What can be shared
Threads in the same process usually **share**:
- the **program code**
- **global/static variables**
- the **heap**

This works because:

#### 1. Code is usually read-only
The machine instructions of the program normally do not change while the program runs.  
So multiple threads can execute the same code at the same time, even from different places in it.

Example:
- Thread A is in `foo()`
- Thread B is in `bar()`
- Both are using the same code segment in memory

They do **not** need separate copies of the instructions.

#### 2. Global variables are meant to be shared
Global variables represent process-wide state.  
If each thread had its own copy automatically, they would no longer be good for communication or coordination between threads.

Example:
```c

```
If all threads increment `counter`, they are intentionally working on the **same variable**.

Of course, this is also why synchronization is needed.

### Important distinction
- **Local variables** → usually on each thread’s **own stack**
- **Global variables** → in **shared memory**
- **Thread-local variables** are a special case: they look global in scope, but each thread gets its own copy

### Short intuition
Threads are like multiple workers in the **same workshop**:
- they share the same tools and materials (**code, globals, heap**),
- but each has their own hands and notepad (**registers, stack, program counter**).

So they don’t need separate copies of code and globals because those are part of the **shared process state**, not the **per-thread execution state**.

10. If a lock guarantees mutual exclusion, why do we need condition variables too?
A)
A lock and a condition variable do different jobs:

- **Lock**: gives **mutual exclusion**  
  → only one thread at a time can access the shared state.

- **Condition variable**: lets a thread **wait until some condition on that shared state becomes true**  
  → without busy-waiting.

Why the lock alone is not enough:

If a thread holds the lock and discovers “I can’t continue yet,” it has a problem:
- If it **keeps the lock**, no other thread can enter and change the state, so the condition may never become true.
- If it **releases the lock and retries manually**, it may waste CPU or miss the right moment unless the waiting is coordinated carefully.

A condition variable solves this by providing an operation like **wait(lock)** that:
1. atomically releases the lock,
2. puts the thread to sleep,
3. later wakes it up,
4. and reacquires the lock before returning.

That atomicity is important; otherwise a thread could **miss a signal** and sleep forever.

So in short:

- **Locks protect shared state.**
- **Condition variables coordinate waiting for changes in that state.**

Typical pattern:

```cpp
lock.acquire();
while (!condition_on_shared_state) {
    cv.wait(&lock);
}
// safe to proceed
lock.release();
```

Without the condition variable, you’d often end up with inefficient polling or incorrect synchronization.

B)
A lock and a condition variable solve different problems:

- **Lock**: gives **mutual exclusion**  
  → only one thread at a time can access shared state.

- **Condition variable**: lets threads **wait until some condition becomes true**  
  → e.g. “buffer is not empty” or “buffer is not full”.

### Why the lock alone is not enough
A lock can protect shared data, but it does **not** provide a good way to say:

> “I can’t continue now, so go to sleep and wake me when the state changes.”

Without a condition variable, a thread would often have to:
- repeatedly check the condition in a loop (**busy waiting**), or
- release the lock and somehow sleep/wake in an unsafe ad hoc way.

### Example
Suppose one thread wants to remove an item from a queue.

- With just a lock:
  - thread locks the queue
  - sees queue is empty
  - now what? It must unlock and keep checking again later

That wastes CPU or becomes tricky to coordinate.

- With a condition variable:
  - thread locks the queue
  - while queue is empty, it calls `wait`
  - `wait` **atomically releases the lock and sleeps**
  - when another thread adds an item, it `signal`s the condition
  - waiting thread wakes up, re-acquires the lock, and checks again

### Key idea
- **Lock** = protects the shared state
- **Condition variable** = coordinates **state-dependent waiting**

So mutual exclusion answers:
> “Who may access the data right now?”

Condition variables answer:
> “When is it meaningful for a thread to proceed?”

11. Why is it incorrect to replace every condition-variable wait with a simple loop that repeatedly checks the condition until it becomes true?
A)
Because that would be **busy waiting** (spinning), and it breaks the main purpose of a condition variable.

A condition-variable wait does **two important things**:

1. **Releases the mutex and sleeps**
   - The waiting thread stops using CPU.
   - Other threads can acquire the lock and change the condition.

2. **Wakes up efficiently when signaled**
   - The thread is resumed when something relevant may have changed.

If you replace it with a loop like:

```c
while (!condition) {
    // keep checking
}
```

then:

- **CPU is wasted**: the thread keeps running just to re-check.
- **It may block progress** if it keeps holding the lock while checking.
- **It scales badly**: many waiting threads can consume lots of processor time.

A correct condition-variable pattern is usually:

```c
pthread_mutex_lock(&m);
while (!condition) {
    pthread_cond_wait(&cv, &m);
}
pthread_mutex_unlock(&m);
```

This is better than spinning because the thread **sleeps instead of burning CPU**, and the mutex is handled correctly while waiting.

So the replacement is incorrect not because the logic of “check until true” is always wrong, but because it loses the **blocking, efficient, and synchronized** behavior that condition variables provide.
B)
Because that would be **busy waiting / polling**, not proper blocking.

With a condition variable, `wait()` does two crucial things:

1. **releases the lock atomically**, and
2. **puts the thread to sleep** until something may have changed.

If you replace it with:

```cpp
while (!condition) {
    // just keep checking
}
```

then problems arise:

- **Wastes CPU time**: the thread spins continuously instead of sleeping.
- **Can block progress** if it keeps holding the lock while checking, because other threads may need that lock to make the condition become true.
- If you release the lock manually and poll again later, you’ve reinvented **inefficient polling**, which is exactly what condition variables are meant to avoid.
- You may need arbitrary delays like `sleep()` or `yield()`, which are unreliable for waiting on shared state. The source explicitly says waiting for object state should use a **condition variable**, not `thread_sleep()` or `thread_yield()`.

So the key idea is:

- **Condition variable wait** = efficient, correct waiting for a state change.
- **Simple repeated checking** = polling, inefficient, and possibly wrong if it interferes with the lock.

In short: a condition variable lets a thread **sleep until notified**, while a simple loop just **keeps burning CPU checking**.

12. If a thread signals a condition variable, shouldn’t the waiting thread run immediately?
A)
No. A condition variable signal does **not** mean “run the waiting thread immediately.”

It means something more like:

> “One waiting thread is now eligible to wake up.”

What happens next depends on the scheduler and the mutex.

### Why not immediately?
A thread waiting on a condition variable usually waits like this:

- it sleeps on the condition variable
- when signaled, it wakes up
- but before continuing, it must **reacquire the associated mutex**

So even after `signal()`:

1. the waiting thread may be moved from **waiting** to **ready**
2. the signaling thread may keep running
3. the awakened thread cannot proceed until it gets the mutex

### Important consequence
If the signaling thread still holds the mutex, the awakened thread usually **cannot continue yet**.

That’s why this pattern is common:

```c
pthread_mutex_lock(&m);
while (!condition) {
    pthread_cond_wait(&cv, &m);
}
/* use condition */
pthread_mutex_unlock(&m);
```

and the signaling side:

```c
pthread_mutex_lock(&m);
condition = true;
pthread_cond_signal(&cv);
pthread_mutex_unlock(&m);
```

The waiting thread wakes up, then competes to lock `m` again.

### So the short answer
- **Signal does not force an immediate context switch**
- **Signal does not transfer the CPU directly**
- **Signal only wakes a waiter so it can eventually run**

B)
Not necessarily.

With most modern condition variables, `signal()` does **not** make the waiting thread run immediately. It only moves one waiting thread from the condition variable’s **wait queue** to the scheduler’s **ready queue**. The waiting thread will run later, when the scheduler chooses it, and it must also **re-acquire the lock** before `wait()` can return.

So the sequence is more like:

1. Thread A holds the lock and changes shared state.
2. Thread A calls `signal()`.
3. One waiting thread B becomes **ready**.
4. A may keep running for a while.
5. Later B gets scheduled.
6. B tries to re-acquire the lock.
7. Only then does B continue after `wait()`.

This is called **Mesa semantics**.

- By the time B actually runs, the shared state may have changed again.
- So waiting code must use:

```c

}
```

not `if`.

So short answer: **No—`signal()` usually means “wake it up so it may run soon,” not “run it right now.”**

13. If deadlock means two threads are stuck waiting forever, how is that different from starvation?
A)
Deadlock and starvation both mean “a thread doesn’t make progress,” but the reason is different:

- **Deadlock**: a set of threads are waiting on each other in a cycle, so **none of them can continue**.
  - Example:  
    - Thread A holds lock 1 and waits for lock 2  
    - Thread B holds lock 2 and waits for lock 1  
    - Both wait forever

- **Starvation**: a thread is continually denied the resource or CPU time it needs, even though **other threads may keep running**.
  - Example:
    - A low-priority thread keeps trying to get a lock
    - Higher-priority threads always get it first
    - The low-priority thread may wait indefinitely

### Key difference
- **Deadlock** = threads are blocked because of a circular wait
- **Starvation** = a thread is postponed indefinitely because scheduling/resource allocation is unfair

So:
- In **deadlock**, everyone in the deadlocked group is stuck.
- In **starvation**, at least one unlucky thread is stuck, while others can still make progress.
B)
Deadlock is a special case of starvation.

- **Starvation:** a thread waits indefinitely because it keeps getting unlucky or postponed.
  - Example: a writer in a readers-writers system never gets the lock because new readers keep arriving.
  - There is **no required cycle** of threads waiting on each other.

- **Deadlock:** a set of threads waits forever in a **cycle**.
  - Thread A waits for Thread B, and Thread B waits for Thread A, or a longer circular chain.
  - None of them can proceed because each is waiting for another in the cycle.

So:

- **All deadlocks cause starvation** for the involved threads.
- **Not all starvation is deadlock.**

A simple way to remember it:
- **Starvation = “I may never get a turn.”**
- **Deadlock = “We are blocking each other in a circle.”**

14. Why can fine-grained locking improve performance in some programs but make others slower or more error-prone?
A)
Fine-grained locking can improve performance because it lets multiple threads work on different parts of a program’s data at the same time, instead of forcing them all to wait for one big lock.

But it can also make programs slower or more error-prone because:

- **More locking overhead:** many small locks mean more lock/unlock operations.
- **More complex code:** it becomes harder to reason about which lock protects what.
- **Higher risk of bugs:** especially **deadlocks**, forgotten locks, or inconsistent locking order.
- **Sometimes little benefit:** if threads still need the same data often, extra locks add cost without much extra parallelism.

So the tradeoff is:

- **Coarse-grained locking** → simpler, safer, but can reduce concurrency.
- **Fine-grained locking** → more concurrency, but more overhead and complexity.

In short: fine-grained locking helps when contention on one big lock is the real bottleneck, but hurts when the added complexity and overhead outweigh the extra parallelism.
B)
Fine-grained locking can improve performance because it reduces contention: different threads can work on different parts of a shared structure at the same time instead of all waiting on one big lock.

Example:
- one lock for the whole hash table → only one thread at a time
- one lock per bucket → threads accessing different buckets can proceed in parallel

But it can also make things worse:

1. **More overhead**  
   More locks means more lock/unlock operations, more bookkeeping, and sometimes higher synchronization cost. If contention was low to begin with, this extra complexity may just slow things down.

2. **More complex operations**  
   Some actions affect multiple parts of the structure, like resizing a hash table. With fine-grained locking, these operations become much harder because they may need several locks or special coordination.

3. **Higher risk of bugs**  
   Multiple locks increase the chance of:
   - deadlock
   - inconsistent state
   - races between parts protected by different locks

4. **Hardware effects**  
   Even when locks are separate, performance can still suffer from shared-cache effects like false sharing or heavy communication between processors.

So the tradeoff is:

- **Coarse-grained locking** → simpler, easier to get correct, but can limit parallelism
- **Fine-grained locking** → more concurrency, but more overhead and much more complexity

That’s why a common rule is: start with a simple locking design, measure performance, and only add finer-grained locking if contention is actually a bottleneck.

15. If one big lock is simpler and correct, why do operating systems ever bother with more complicated synchronization designs?

- harder correctness reasoning

16. Why can acquiring two locks in different orders be dangerous even if each individual lock is used correctly?
A)
Because the danger is not in each lock by itself, but in the **interaction between multiple locks**.

If two threads acquire the same two locks in different orders, you can get **deadlock**:

- Thread 1 acquires **lock A**, then tries to acquire **lock B**
- Thread 2 acquires **lock B**, then tries to acquire **lock A**

Now:

- Thread 1 waits for B, which Thread 2 holds
- Thread 2 waits for A, which Thread 1 holds

Neither can continue, so both are stuck.

So even though:

- each lock is used “correctly” on its own,
- and each critical section may be properly protected,

the program can still fail because the threads create a **cycle of waiting**.

Example:

```text
Thread 1: lock(A) -> lock(B)
Thread 2: lock(B) -> lock(A)
```

This is why a common rule is:

- **always acquire multiple locks in a consistent global order**

For example, always lock A before B. That prevents the circular wait.
B)
Because **correct use of each lock individually does not guarantee correctness when multiple locks interact**.

The danger is **deadlock**:

- Thread A locks **L1**
- Thread B locks **L2**
- Then A tries to lock **L2**
- B tries to lock **L1**

Now:
- A waits for B to release **L2**
- B waits for A to release **L1**

Neither can continue, so both are stuck.

So the problem is not “using a lock wrong” — each lock may be properly acquired and released — but that **inconsistent lock ordering creates a circular wait between threads**.

A common prevention is to **always acquire multiple locks in the same global order**.

18. If disabling interrupts can prevent races on a uniprocessor, why not just use that technique everywhere instead of locks?
A)
Because it only works in a very limited case.

- **On a uniprocessor:** disabling interrupts can make a short kernel code sequence effectively atomic, because no timer interrupt means no preemption, so no other thread runs on that CPU in the middle of the sequence.
- **But not on a multiprocessor:** turning off interrupts on one CPU does **not** stop other CPUs. Threads on other processors can still access the same shared data, so races still happen. That’s why multiprocessors need **atomic instructions and locks**.

Even on a uniprocessor, using interrupt disabling everywhere is a bad idea:

- **System becomes unresponsive** if interrupts stay disabled too long.
- **No timer interrupts → no scheduling**, so other threads cannot run.
- **I/O and user input handling are delayed**, which hurts real-time responsiveness.
- It is only safe in **trusted kernel code**; user code must not be allowed to disable interrupts, or it could monopolize the processor.

There’s also a subtle issue with interrupts and locking:

- If an interrupt handler uses shared data, code accessing that same data often must **disable interrupts before taking the spinlock**, otherwise the handler could interrupt the thread and deadlock waiting for a lock the interrupted thread already holds.

So the short answer is:

**Disabling interrupts is a low-level tool for short kernel critical sections on a uniprocessor; locks are the general mechanism because they also work on multiprocessors and don’t freeze interrupt handling for long periods.**
B)

1. **Scalability / SMP correctness**

4. **It only blocks some kinds of interference**

- **Disable interrupts**: useful for very short critical sections in the kernel on a **uniprocessor**.
- **Locks**: general solution, especially for **multicore systems**.

19. Why can a scheduler that maximizes throughput still make a system feel slow to users?

3. **Users notice latency, not overall efficiency**

   - response time
   - delay before input is handled
   - smoothness of interaction

So a system can be **efficient overall** but still **feel sluggish** if it does not give quick service to interactive or time-sensitive processes.

In short: **maximizing throughput optimizes total work done, not how fast the system responds to a user right now.**

- **Response time** = how long a user waits for one task to get a result.

A scheduler can maximize throughput by favoring policies with **low overhead** and long uninterrupted runs, such as FIFO. That can complete a lot of total work efficiently, but it may let a **long task block short interactive tasks** behind it.

- poor interactivity,

20. If round robin gives every job a turn, why isn’t it always the fairest or best scheduling policy?
A)
Round robin is **fair in one sense**: every runnable job gets CPU time regularly.

But it’s **not always the best or fairest overall** because “fair” can mean different things:

- **Different jobs have different needs.**

- **Turn-taking can hurt performance.**

- **It doesn’t minimize waiting or turnaround time.**

- **It ignores priority/importance.**  
  A critical system task and a background job get the same share unless extra priority rules are added.

- **I/O-bound vs CPU-bound jobs behave differently.**  
  I/O-bound jobs often use only a little CPU and then block. CPU-bound jobs keep using full quanta. Equal turns don’t always feel fair in terms of responsiveness.

So the key idea is:

**Round robin is fair in CPU share, but not always fair in response time, completion time, or job importance.**

21. Why can shortest-job-first reduce average waiting time even though it seems unfair to long jobs?
A)
Because SJF optimizes the **order of waiting**.

If you run a **short job first**, it finishes quickly and only delays the long job by a little.  
But if you run a **long job first**, every short job behind it has to wait a long time.

So one long job can make many short jobs wait a lot, while many short jobs only make one long job wait a little. That usually makes the **average waiting/response time smaller**.

- Jobs: `10, 1, 1`
- **Long first**: waits = `0, 10, 11` → average = `7`
- **Short first**: waits = `0, 1, 2` for the short jobs, long job waits `2` → average = `1`

More generally, if a scheduler ever chooses a longer job before a shorter available one, swapping them makes the average waiting time smaller.

- Long jobs may wait a very long time.
- If short jobs keep arriving, a long job may even **starve**.

B)

Order: A, B, C

Waiting times:

22. If a machine has multiple CPUs, why can’t the operating system just keep every thread on whichever CPU is free at the moment?
A)
Because moving a thread between CPUs is not free.

On a multiprocessor, a thread often has **CPU affinity**: if it ran on CPU 2 before, it’s better to run it again on CPU 2. The main reason is **cache reuse**. That CPU may still have the thread’s data and instructions in its cache, so resuming there is fast. If the OS sends the thread to a different CPU “just because it’s free,” the new CPU may need to reload that working set, which costs time.

That’s why systems like Linux often use **per-processor run queues** and try to return a thread to the same processor. They only **rebalance** work across CPUs when the imbalance lasts long enough that the benefit outweighs the cache-miss cost.

So the tradeoff is:

- **Always use any free CPU** → better short-term load balance
- **Keep threads on the same CPU** → better cache performance, less migration overhead

Real OS schedulers try to balance both, not just pick any free CPU immediately.
B)
Because moving a thread between CPUs is not free.

The main reason is **cache locality**:

- When a thread runs on CPU 1, that CPU’s caches start filling with the thread’s data and instructions.
- If the OS later moves that thread to CPU 2, CPU 2’s caches are likely missing that useful data.
- Then the thread has to reload a lot from main memory, which is much slower.

So even if another CPU is “free,” migrating the thread may make it run **worse**, not better.

There are also a few other costs:

- **Migration overhead**: the OS has to stop scheduling it on one CPU and place it on another.
- **Cache coherence / shared data effects**: if threads share data, moving them around can increase memory traffic.
- **NUMA effects** on some systems: memory may be physically closer to one CPU than another, so moving a thread can make memory accesses slower.

So schedulers usually try to balance two goals:

1. **Keep CPUs busy**
2. **Keep threads on the same CPU when possible** (called **processor affinity**)

So the OS does not just pick “any free CPU” every time, because **stability of placement often improves performance**.

23. Why does processor affinity matter if all CPUs are supposed to be equivalent?

- **NUMA locality**:

- **Lower migration overhead**:  
  Moving threads between CPUs isn’t free. The OS may need to rebalance load, and migrations can hurt throughput.

- **Predictability**:  
  Keeping a task on specific CPUs can reduce jitter, which matters for real-time or latency-sensitive workloads.

Why the CPUs still seem “equivalent”:
- They execute the same instruction set.
- Any thread can usually run on any CPU.

But the **surrounding state** is different:
- each core has different cache contents,
- each socket may have different memory distance,
- some systems mix performance and efficiency cores.

So affinity matters not because CPUs are functionally different, but because **where a thread runs affects performance**.

24. If utilization close to 100% sounds efficient, why do systems often become much less responsive as utilization approaches 100%?
A)
Because near **100% utilization**, the system has almost **no slack** left.

Even if the **average** arrival rate is just below the **service rate**, real workloads are not perfectly regular:
- requests arrive in **bursts**
- service times vary
- sometimes several jobs arrive close together

When that happens, incoming work has to **wait in a queue**. At low utilization, the server can catch up during quieter moments. But near 100% utilization, it is already busy almost all the time, so it cannot absorb those fluctuations. The queue grows, and **response time rises sharply**.

That’s why response time is **nonlinear** with utilization:
- at low load, a small increase in utilization causes only a small delay increase
- near full utilization, even a tiny load increase can make delay explode

A standard queueing result is:

\[
R = \frac{S}{1-U}
\]

where:
- \(R\) = response time
- \(S\) = service time
- \(U\) = utilization

So:
- at \(U = 0.9\), \(R = 10S\)
- at \(U = 0.95\), \(R = 20S\)

Just 5% more utilization can **double** response time.

And if arrival rate exceeds service rate (\(\lambda > \mu\)), the system is in **overload**: the queue keeps growing and waiting time can become unbounded.

So the short answer is: **high utilization looks efficient, but it removes the buffer needed to handle randomness, causing queues and delays to blow up.**
B)
Because high **utilization** usually means there’s almost **no spare capacity** left to absorb randomness.

In real systems, work doesn’t arrive perfectly evenly and service times aren’t perfectly constant. So when utilization is, say, 95–99%:

- new requests keep arriving,
- the server is almost always busy,
- even a small burst creates a queue,
- and that queue takes a long time to drain because there’s very little idle time available to catch up.

So responsiveness gets worse not because the system is “doing less work,” but because **waiting time grows very rapidly** as utilization nears 100%.

A common queueing result shows this effect:

\[
\text{Response time} \propto \frac{1}{1-\rho}
\]

where \(\rho\) is utilization.

So:
- at 50% utilization: manageable,
- at 90% utilization: delays grow a lot,
- at 99% utilization: delays can explode.

In short: **100% utilization is efficient for throughput, but terrible for latency and responsiveness.** Systems need some slack capacity to stay responsive.

25. If the operating system already protects processes from one another, why do we also need user mode and kernel mode?
A)
Because “the OS protects processes” is only possible if the hardware gives the OS a way to enforce that protection.

Without user mode vs. kernel mode:

- any program could execute dangerous instructions directly
- any program could access arbitrary memory or devices
- any program could bypass the OS completely

So the OS alone is not enough, because application code runs on the same CPU. If there were no privilege distinction, a buggy or malicious process could simply overwrite another process, the OS, or the disk.

The two modes solve this:

- **Kernel mode**: the OS runs with full privileges
- **User mode**: applications run with restricted privileges

This lets the OS:

- block **privileged instructions** in applications
- enforce **memory protection**
- regain control with **timer interrupts**
- handle safe entry into the kernel via **system calls**

28. Why does the operating system need timer interrupts at all? Why not just let each program run until it blocks or finishes?

- **Preemption / fairness:**

- **Responsiveness:**

**Timer interrupts are needed so the OS can preempt running programs and ensure fairness, responsiveness, and control of the CPU.**
B)
Because without timer interrupts, the OS can’t reliably take the CPU back from a running program.

- **blocks** (e.g. waits for I/O), or
- **finishes**,

then this only works if the program voluntarily gives up the CPU. A program that:

- has an infinite loop,
- does long computation without blocking,
- or is buggy/malicious,

could keep running forever and **freeze out everything else**.

A **timer interrupt** lets the hardware interrupt the currently running program after some amount of time. That gives the OS a chance to:

- **preempt** the program and run another one
- enforce **fair CPU sharing**
- keep the system **responsive**
- implement **time slicing** in multitasking systems

The system would be doing **cooperative multitasking**: each program must behave nicely and yield control. That’s fragile, because one bad program can hang the whole system.

## In short

Timer interrupts are needed so the OS stays **in control of the CPU**, instead of trusting every program to give it back voluntarily.

31. If a child process is created from a parent process, why doesn’t every process creation require copying the parent’s entire memory immediately?
A)
Because modern OSes usually use **copy-on-write**.

When a process is created with something like **UNIX `fork`**, the child initially gets an address space that **looks like** a full copy of the parent, but the OS does **not** immediately copy all physical memory. Instead:

- parent and child temporarily **share the same memory pages/segments**
- those shared regions are marked **read-only**
- if either process tries to **modify** one of them, a fault occurs
- only then does the OS make a **real physical copy** of that page/segment

So the child behaves as if it has its own memory, but copying is **deferred until needed**.

This is efficient because in the common case, the child soon calls **`exec`** to load a new program, so most of the parent’s memory never needs to be copied at all. Often only something small, like the **stack**, gets copied before `exec`.

So: **process creation doesn’t require immediate full copying because the OS uses copy-on-write to avoid unnecessary memory duplication.**

33. If a TLB is only a cache of address translations, why can TLB misses have such a noticeable effect on performance?
A)
Because a TLB miss is not “just a cache miss” in the usual sense — it delays **every memory access** that needs translation.

A TLB caches recent virtual-page → physical-page translations. On a **hit**, translation is very fast. On a **miss**, the CPU must do the **full address translation**:

- either a **page table walk in hardware**, or
- trap into the **OS kernel** on systems with a software-managed TLB.

That extra work is expensive compared to a TLB lookup.

From the provided context, the cost is roughly:

**Cost(address translation) = Cost(TLB lookup) + Cost(full translation) × (1 − P(hit))**

So even if misses are rare, each miss is much more expensive than a hit.

Why this matters so much:

- **Translation happens on every instruction fetch and data load/store**, not just occasionally.
- A full translation may require **multiple memory lookups**.
- On software-loaded TLBs, a miss may require a **kernel trap**, which is even slower.
- The source notes that on modern x86, a hardware-resolved TLB miss can still be around the equivalent of **~17 instructions** in the best case, while a kernel trap can cost **hundreds to thousands of instructions**.

So the short answer is:

**TLB misses are noticeable because address translation is on the critical path of almost every memory reference, and a miss replaces a very fast lookup with a much more expensive translation process.**
B)
Because a TLB miss doesn’t just mean “one extra cache lookup.” It can stall the whole memory access.

A virtual memory access normally works like this:

- CPU has a **virtual address**
- TLB gives the **physical address** quickly
- then the cache/memory can be accessed

If the TLB **misses**, the CPU must do a **page table walk** to find the translation. That is expensive because:

- the page table is in **memory**
- a walk may require **multiple memory accesses** per miss
- during that time, the original load/store can’t complete

So one TLB miss can cost much more than a normal cache miss in terms of delay.

Why this matters a lot:

- **Every memory reference** needs address translation
- programs often make **many memory accesses**
- if the working set of pages is larger than what the TLB can cover, misses can happen frequently
- the penalty is repeated over and over

In short:  
A TLB miss is noticeable because translation is on the critical path of every memory access, and recovering from a miss may require several extra memory reads before the actual data access even begins.

38. If virtual memory lets the OS move pages between RAM and disk, why doesn’t that mean programs can effectively use unlimited memory with little downside?

- page faults happen frequently
- overall performance can collapse

- only a small fraction of the program’s pages are actively used at once

It works poorly when:
- the active data is larger than physical RAM

### So the key idea
Virtual memory gives:
- **convenience**
- **protection**
- **the illusion of a larger memory space**

But it does **not** give unlimited memory “with little downside,” because the downside is potentially **massive slowdown** once disk-backed pages are accessed often.

B)
Because **disk is vastly slower than RAM**.

- memory access is fast
- fetching a page from disk can be **orders of magnitude slower**

- **more flexibility**

39. What exactly is a page fault, and why is it not always an error?
A)
A **page fault** happens when a program tries to access a **virtual memory page** that is **not currently mapped in physical RAM** in the way the CPU expects.

When this happens, the CPU raises an exception, and the **operating system** handles it.

Why it is **not always an error**:

- **Normal page fault:** the page is valid, but just not in RAM right now.
  - Example: it was swapped out to disk, or it hasn’t been loaded yet.
  - The OS brings the page into memory, updates the page table, and the program continues.
- **Invalid page fault:** the program accessed memory it is not allowed to use.
  - Example: dereferencing an invalid pointer.
  - In that case, the OS cannot fix it, so it turns into an error like a **segmentation fault**.

So the key idea is:

- **Page fault = mechanism/exception**
- **Segmentation fault or access violation = actual error outcome when the fault is invalid**

In short, a page fault is often just part of how **virtual memory** works, not necessarily a bug.
B)
A **page fault** is an **exception/trap raised by the hardware** when a process accesses a virtual page whose page table entry is **not currently valid for that access**.

In practice, this can happen in two common cases:

1. **The page is not in physical memory right now**  
   - The hardware checks the page table, sees the entry is invalid, and traps to the kernel.
   - The OS can then **load the page from disk into a page frame**, update the page table, and resume the process.

2. **The access violates permissions**  
   - Example: writing to a read-only page.
   - In that case, the trap is also a page fault/protection fault, but the OS may decide the program did something illegal.

So it is **not always an error** because many page faults are part of **normal demand paging**:
- programs start before all their pages are loaded,
- the OS brings pages into memory **only when first used**,
- mapped files may also be loaded on first access.

Only some page faults are actual errors, such as:
- accessing an unmapped address,
- violating protection in a way the OS cannot handle.

So the short version is:

- **Page fault = “this memory access cannot proceed right now as-is.”**
- It may be **handled normally** by the OS,
- or it may indicate a **real bug/illegal access**.

40. If caches are supposed to speed things up, why do some access patterns still perform badly even when the same total amount of data is used?
A)
Because cache performance depends less on the total amount of data and more on how that data is accessed over time.

The key idea is locality:

- Temporal locality: if you use the same data again soon, it’s likely still in the cache.
- Spatial locality: if you use nearby data, fetching one block helps with future accesses too.

So two programs can use the same total amount of data, but behave very differently:

- Good pattern: repeatedly accesses the same small region or nearby addresses  
  → high cache hit rate, fast
- Bad pattern: jumps around through many locations before reusing anything  
  → data gets evicted before it is needed again, causing many cache misses

A cache only helps when the recently accessed data is likely to be useful again soon. If the access pattern has little locality, the cache cannot predict well, so performance stays poor.

This is why even with the same total data size, one workload may fit the cache’s “working set” at a given moment and another may not. In the bad case, the system keeps fetching data from slower memory instead of reusing cached copies.
B)
Because caches care a lot about **how** data is accessed, not just **how much** data is accessed.

Two programs can use the same total amount of data, but one can run much faster if its access pattern matches what caches are good at.

### Why this happens

Caches work best when there is:

- **Temporal locality**: you use the same data again soon
- **Spatial locality**: you use nearby data soon

If your program does this, the cache can keep useful data close to the CPU.

If it doesn’t, you get lots of **cache misses**, and the CPU has to fetch data from slower memory.

### Example

Suppose you have an array.

- **Good pattern:** read `a[0], a[1], a[2], a[3], ...`
  - Arrays are stored contiguously
  - One cache line fetch brings in several nearby elements
  - So many later accesses are already in cache

- **Bad pattern:** read `a[0], a[1000], a[2000], a[3000], ...`
  - Each access may touch a different cache line
  - Much less reuse
  - More misses, slower execution

### Same total data, different performance

Even if both patterns eventually touch the same number of bytes:

- one may reuse cache lines efficiently,
- the other may constantly evict useful data before reusing it.

So performance depends on:
- **order of access**
- **reuse distance**
- **stride**
- **whether accesses map to the same cache sets** in unlucky ways

### In short

Caches speed up programs only when the access pattern has good locality.  
If the pattern has poor locality or causes many conflicts, performance can still be bad even with the same total data size.

41. Why can a program’s working set matter more for performance than its total size?
A)
Because performance depends mostly on the data and code the program is using *right now*, not everything it could possibly use.

The **working set** is the “active” subset of memory a program repeatedly touches over a period of time. If that working set fits in a fast level of the memory hierarchy—cache or main memory—then most accesses are hits, and the program runs quickly.

If it does **not** fit, the system keeps evicting and reloading data, causing many cache misses or page faults. That can slow the program dramatically, even if the program’s **total size** is not huge.

So:

- **Total size** = all code/data the program has
- **Working set** = the part currently being used frequently

Why working set matters more:
- A large program can still run fast if only a small active portion is used at a time.
- A smaller program can run poorly if its active data does not fit in cache or memory.
- Once the working set no longer fits, performance can collapse due to thrashing.

In short: **the memory hierarchy cares about locality, and the working set captures locality better than total program size.**
B)
Because performance usually depends more on **what memory the program is actively using right now** than on how much memory it owns in total.

- **Total size** = all memory the program has allocated.
- **Working set** = the subset of that memory being used frequently during a given time period.

Why this matters:

1. **Caches and RAM are limited**
   - If the working set fits in cache or main memory, access is fast.
   - If it does not fit, the CPU gets lots of cache misses or the OS may need to swap pages, which is much slower.

2. **Unused memory doesn’t hurt as much**
   - A program might allocate a lot of memory, but if most of it is rarely touched, it won’t strongly affect current execution speed.

3. **Locality drives speed**
   - Programs with a small, tightly reused working set benefit from temporal and spatial locality, so the hardware can serve data quickly.

Example:
- Program A uses **2 GB total**, but repeatedly works on only **10 MB** at a time.
- Program B uses **200 MB total**, but constantly jumps around all **200 MB**.

Program A may run faster if its 10 MB working set fits well in cache/RAM, while Program B may suffer more misses despite being smaller overall.

So, **working set matters more because it determines whether the memory the program actually needs right now can stay in fast storage levels**.

42. If LRU sounds smarter than FIFO, why don’t systems always implement perfect LRU?
A)
Because **perfect LRU is expensive to implement**, especially in hardware.

LRU is “smarter” because it uses **recent history** to predict future use, and that often works well when there is **temporal locality**. But to implement **perfect** LRU, the system must know the exact recency order of all cached blocks/pages and update that order on **every access**.

Why that’s a problem:

- **High bookkeeping cost**: you need extra metadata for each block.
- **Work on every hit/miss**: every reference may require reordering items.
- **Too complex for fast hardware caches**: maintaining something like a full ordered list at high speed is impractical.
- **Space tradeoff**: the extra tracking data can consume memory that could otherwise be used for a larger cache.

So in practice, systems often use:

- **approximations of LRU** for hardware/page replacement,
- or simpler policies like **FIFO**, **Clock**, or hybrids,
- depending on workload and implementation cost.

Also, LRU is not always better: on some patterns, like **repeated scans through data larger than the cache**, LRU can perform just as badly as FIFO.

So the short answer is: **perfect LRU can improve decisions, but its implementation cost and complexity are often not worth it.**
B)
Because **perfect LRU is expensive to implement**, especially in hardware.

LRU often gives better eviction choices than FIFO because it uses **recent usage history**, but to do that perfectly, the system must know the **exact order of accesses** to all items/pages/cache lines.

That creates problems:

- **High bookkeeping overhead**  
  On every access, you’d need to update metadata to maintain the full recency ordering.

- **Hardware complexity**  
  In CPU caches, tracking exact LRU for many lines in a set requires extra bits and logic, which gets costly and slow.

- **Scalability issues**  
  As the number of entries grows, perfect LRU becomes harder to maintain efficiently.

So in practice, systems often use:

- **approximations of LRU** for caches and virtual memory
- sometimes **FIFO or Clock**, because they are much simpler and cheaper

So the short answer is:

**Perfect LRU may make better decisions, but its implementation cost can outweigh its benefit.**

43. How can adding more page frames ever make a paging policy perform worse?
A)
Because of **Belady’s anomaly**.

Some page replacement policies, especially **FIFO**, are **not stack algorithms**. That means when you give them more page frames, the set of pages kept in memory with \(n\) frames is not guaranteed to be a subset of the pages kept with \(n+1\) frames.

So with more memory, the policy can make **different replacement decisions** that are actually worse for a particular reference string, causing **more page faults**.

### Intuition
You’d expect:
- more page frames → more pages can stay in memory
- therefore fewer page faults

That is true for policies like **LRU** and **MIN**, but **not for all policies**.

### Classic example with FIFO
Reference string:
\[
1,2,3,4,1,2,5,1,2,3,4,5
\]

- With **3 frames**, FIFO gives **9 page faults**
- With **4 frames**, FIFO gives **10 page faults**

So adding a frame made performance worse.

### Why this happens
FIFO only cares about **arrival order**, not how likely a page is to be used again.  
When memory size changes, the eviction order changes too, and that can accidentally evict pages that would soon be needed.

### Key point
Adding more frames can hurt **only for some policies**.  
Policies like **LRU** avoid this because they have the **stack property**: pages in memory with fewer frames are always included in the pages in memory with more frames.

B)
Because of **Belady’s anomaly**.

Normally, you’d expect more page frames ⇒ fewer page faults. But with some paging policies, especially **FIFO**, adding frames can actually cause **more** faults.

### Why?
FIFO evicts the page that has been in memory the longest, regardless of how useful it still is.

So when you add an extra frame, the set of pages kept in memory changes. That can cause FIFO to throw out a page that would soon be needed, even though with fewer frames it would have stayed.

### Classic example
Reference string:
**1 2 3 4 1 2 5 1 2 3 4 5**

- With **3 frames**, FIFO gives **9 page faults**
- With **4 frames**, FIFO gives **10 page faults**

So more memory made performance worse.

### Key idea
This happens because FIFO does **not** have the **stack property**:
- In a stack algorithm, pages in memory with `n` frames are always a subset of those with `n+1` frames.
- FIFO does not guarantee that, so increasing frames can change eviction decisions in a bad way.

Policies like **LRU** and **Optimal** do have the stack property, so they do **not** suffer from this anomaly.

45. If zero-copy I/O avoids copying data, where does the data actually live while it is being moved?
A)
In zero-copy I/O, the data still lives in memory — just not in two separate places.

Typically, with normal I/O:

1. device transfers data into a kernel buffer
2. kernel copies it into a user buffer

With zero-copy I/O, the goal is to avoid that second memory-to-memory copy across the kernel/user boundary.

So the data usually lives in one of these places:

- **A kernel buffer page** in main memory, and the OS remaps the process’s page table so the user process now sees that same physical page as its own buffer.
- **Directly in the user buffer** in main memory, if the hardware can DMA to/from virtual addresses or the user pages are prepared for the device transfer.

So “zero-copy” does **not** mean “no memory involved.” It means:

- no extra **CPU copy** from kernel memory to user memory
- the same physical memory page is reused or directly filled

In short: the data lives in **RAM pages**, either first in a kernel-owned page that gets **remapped**, or directly in the **user process’s pages**.
B)
It still lives in memory — just not in multiple places.

Usually the data is in one of these places:

- **Kernel buffers / page cache**: when the OS reads from disk or prepares network data
- **DMA-capable device buffers**: hardware like NICs or disks can transfer data directly to/from RAM
- **User-space memory**: in some zero-copy mechanisms, the kernel maps the same physical memory into user space instead of copying it

So “zero-copy” usually means:

- no extra **CPU-driven copy** between kernel space and user space, or
- fewer intermediate buffers

Example:
- **Traditional I/O**: disk → kernel buffer → user buffer → socket buffer
- **Zero-copy-style I/O**: disk data stays in kernel/page cache and is sent directly to the network interface, often via DMA

So the data does not “float between places” — it always exists somewhere physical, usually in RAM, and zero-copy tries to **reuse or remap the same memory** instead of duplicating it.

47. Why can copy-on-write make operations like process creation or snapshotting much cheaper than they first appear?
A)
Copy-on-write makes them cheaper because the system initially avoids copying the actual data.

Instead of duplicating all memory or disk blocks immediately, it:

- creates a new reference to the same data
- marks that data as shared/read-only
- only makes a real copy later if one side tries to modify it

So for operations like:

- **process creation (`fork`)**: parent and child can initially share the same memory pages
- **snapshotting**: the snapshot and the live system can initially share the same blocks

This is much cheaper because:

- **less data is copied upfront**
- **less time is spent during creation**
- **less memory/storage is used unless changes actually happen**

In many cases, a lot of the shared data is never modified, so the expensive copying never happens at all.
B)
Because copy-on-write avoids doing the full copy up front.

Instead of immediately duplicating all memory, the OS lets the two “copies” share the same physical pages at first, and marks those pages read-only. As long as neither side writes to a page, no real copy is needed.

Then:

- on `fork`, parent and child can initially share memory
- on snapshot/checkpoint, the current state can be preserved without copying every page immediately
- only when someone tries to modify a page does a trap occur
- the OS then copies just that page, and the writer gets its own private version

So the operation becomes cheap because:

1. **Most pages may never be written.**  
   For example, after `fork`, the child often quickly calls `exec`, so copying the parent’s whole address space would have been wasted.

2. **Work is deferred and reduced.**  
   The system copies only the pages that are actually modified, not the entire region.

3. **Initial setup is mostly page-table changes.**  
   The OS usually only needs to copy/update page table entries and mark pages read-only, which is far cheaper than copying all physical memory.

In short: **copy-on-write turns a potentially huge eager memory copy into a small bookkeeping step plus a few on-demand page copies.**

49. Why do modern file systems often use extents or tree-based metadata instead of simple linked allocation?
A)
Because linked allocation scales poorly and gives weak performance.

Modern file systems prefer **extents** and **tree-based metadata** because they better satisfy the main goals of file storage:

- **efficient random access**
- **good sequential performance**
- **support for large files**
- **low overhead for small files**
- **better locality**

### Why simple linked allocation is weaker
With linked allocation, each block points to the next block.

That means:

- **Random access is slow**: to get block *n*, you often have to follow the chain from the beginning.
- **Poor locality**: blocks can end up scattered all over disk, hurting sequential reads.
- **Poor scalability**: very large files require long chains.
- **Metadata lookup is less efficient** than structured indexing.

### Why trees help
Tree-based metadata lets the file system locate any file block more directly.

Advantages:

- **Fast lookup of arbitrary blocks**
- **Scales to large files**
- **Supports both small and large files efficiently**
- High-fanout trees are especially good on disk because reading one index block can cover many data blocks.

FFS, for example, uses a fixed multi-level tree; NTFS and newer systems use more flexible trees.

### Why extents help
An **extent** represents a contiguous range of blocks instead of indexing each block one by one.

Advantages:

- **Less metadata**: one extent can describe many blocks
- **Better sequential I/O**: contiguous data is faster to read/write
- **Works well for large files**
- Trees over extents stay shallow unless the file is badly fragmented

So compared to linked allocation, extents + trees give a file system a much better combination of:

- **random access**
- **sequential performance**
- **scalability**
- **space efficiency in metadata**

In short: **linked allocation is simple, but extents and trees are much faster and more scalable for modern workloads.**
B)
Because simple linked allocation scales poorly.

Main reasons modern file systems prefer **extents** or **tree-based metadata**:

- **Faster random access**  
  In linked allocation, to reach a block in the middle of a file, you often have to follow the chain block by block. That’s slow.  
  Extents and trees let the system find file regions much more directly.

- **Less metadata overhead**  
  Linked allocation stores a pointer for each block or relies on pointer chains.  
  An **extent** represents a whole contiguous range of blocks, like “blocks 1000–1200 belong to this file,” so one record can describe many blocks.

- **Better performance for large files**  
  Modern files are often large. Managing them block-by-block is inefficient.  
  Extents are much more compact, and trees organize many extents efficiently.

- **Better handling of fragmentation**  
  Linked allocation can tolerate noncontiguous blocks, but it doesn’t help much with efficient layout.  
  Extents encourage larger contiguous regions, which improves sequential read/write speed.

- **Scalability**  
  Tree structures scale well when files or directories become very large.  
  They support efficient lookup, insertion, and growth without scanning long chains.

- **Reliability and recovery**  
  A broken pointer in linked allocation can lose part of a file.  
  Modern metadata structures are usually more robust and work better with journaling or copy-on-write designs.

In short:  
**linked allocation is simple, but extents and trees are much more efficient, scalable, and reliable for modern storage systems.**
